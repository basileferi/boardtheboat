# 0004. UUIDv7 primary keys and the schema invariants around them

- **Status:** accepted
- **Date:** 2026-09-30

## Context

URLs must not expose auto-increment identifiers: the count of companies, offers or accounts is
business information, and sequential ids invite enumeration of other users' resources. The usual
alternative — an internal `INT` primary key plus a public `uuid` column — means every route has
to translate between two identities, and every repository method has to pick the right one.

MariaDB has no native UUID column, so Symfony's Doctrine type stores a UUID as `BINARY(16)`.
Random UUIDv4 keys in a clustered InnoDB index cause page splits and index bloat; UUIDv7 is
time-ordered, so inserts stay at the right-hand edge of the index like an auto-increment would.

## Decision

Every entity uses a **UUIDv7 primary key**, generated by
`Symfony\Bridge\Doctrine\IdGenerator\UuidGenerator` (whose default factory is UuidV7) and stored
as `BINARY(16)`. There is no separate public id. Three schema invariants go with it:

1. **InnoDB, explicitly.** WAMP's MariaDB defaults to MyISAM, which accepts a `CREATE TABLE`
   carrying foreign keys and then silently discards them — the first migration was generated,
   applied, and left every relation unconstrained before this was caught. `default_table_options`
   now pins `engine: InnoDB` alongside `charset: utf8mb4` / `collation: utf8mb4_unicode_ci`
   (MariaDB 11.4 would otherwise pick `utf8mb4_uca1400_ai_ci`, which the host may not offer).
2. **Deletion is the database's job.** Every user-owned relation carries
   `ON DELETE CASCADE`, and the audit trail (`import_batch.created_by`) carries `ON DELETE SET
   NULL`. Account deletion is therefore a single `remove()`, proven by a test that deletes an
   account and asserts its applications, views, templates and profile are gone while catalogue
   companies survive.
3. **Full-text search stays in the mapping.** `job_offer` declares
   `#[ORM\Index(columns: ['title', 'description'], flags: ['fulltext'])]`, so
   `doctrine:schema:validate` keeps it honest, and DQL reaches it through the custom
   `MATCH_AGAINST` function in `src/Doctrine/Query/`. Search terms always travel as a bound
   parameter.

Two denormalised fields support the pipeline rather than the UI: `Company::$normalizedName` and
`$domain` are the deduplication keys (SIREN, then domain, then normalised name), and the
`fingerprint` columns on `Company` and `Profile` are hashes of exactly the fields that feed the
relevance score, so a nightly run rescores only the pairs that actually changed.

## Consequences

- Raw SQL debugging shows binary ids; use `HEX(id)` or the app to read them.
- Routes take a UUID and repositories never expose a numeric id — there is no second identity to
  get wrong.
- Any future engine change (to PostgreSQL, say) would cost the full-text index and the
  `MATCH_AGAINST` function; ADR 0002 already rules that out.
- `Profile::refreshFingerprint()` is called from the setters, **not** from a `preUpdate`
  callback: Doctrine ignores property writes made during `preUpdate` unless they go through the
  changeset, so a callback would have stored a stale hash.
